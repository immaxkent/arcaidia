1. Executive decision
Arcaidia V1 is not a new canonical bridge. It is a fast settlement layer above Circle CCTP. The user's source USDC 
is committed to CCTP first. Only after that commitment is observed and independently verified may an 
autonomous liquidity agent advance destination USDC from an destination-chain LP vault. CCTP then completes 
asynchronously and replenishes the LP.
Core invariant: Fast settlement accelerates the user experience; canonical settlement remains the source of 
economic finality.
 Onchain contracts hold funds, enforce replay protection and define authoritative state.
 Offchain agents observe, price risk and decide whether to advance liquidity.
 The Graph is the live discovery/state layer, but never the sole authority for moving pooled funds.
 Circle Agent Wallets provide bounded machine signing authority.
 CCTP is initiated before the fast fill, materially reducing LP settlement risk.
 If no solver fast-fills, canonical CCTP delivery remains the fallback path.

5. Exact V1 transaction sequence
Figure 3. Fast user settlement and asynchronous canonical settlement.
1. Authenticate. User signs in with Privy and obtains/uses an Ethereum wallet.
2. Construct intent. Frontend defines input token, amount, source chain, destination chain, recipient, max fee, 
deadline and nonce.
3. Commit source funds. The Ethereum ArcaidiaIntentRouter pulls USDC and, in the same source transaction 
where feasible, initiates the CCTP Ethereum Arc transfer. It emits IntentCreated with intentId and CCTP →
reference/message metadata.
4. Observe. The Graph indexes the real IntentCreated event and relevant vault/settlement state. The Liquidity 
Agent consumes this live feed.
5. Verify. Before risking LP capital, the Liquidity Agent independently checks Ethereum RPC receipts/logs: 
successful router call, immutable parameters, USDC amount, recipient, Arc destination, CCTP initiation, 
confirmations and no prior fill.
6. Decide. The agent evaluates Arc available liquidity, reserve floor, outstanding unsettled exposure, intent 
size, user fee ceiling, settlement backlog and risk limits.
7. Authorise. If accepted, the Circle Agent Wallet signs an EIP-712 FillAuthorization containing intentId, source 
chain, source transaction hash, recipient, input/output amount, fee, expiry and nonce.
8. Fast fill. ArcaidiaLiquidityVault verifies signer authorisation, replay protection, expiry, limits and liquidity, 
marks intent consumed, then transfers output USDC to recipient.
9. User completion. UI marks FAST_FILLED only after Arc transaction confirmation. The user is done.
10. Canonical completion. CCTP continues independently. Settlement Agent submits/observes the destination 
message flow. SettlementReceiver receives canonical USDC.
11. Reimburse or fallback. If the intent was fast-filled, canonical USDC replenishes LP inventory. If it was not 
fast-filled, canonical USDC is delivered to the intended recipient.
12. Finalise. Intent becomes SETTLED after canonical receive and reconciliation. The Graph indexes the final 
state.

7. Agent verification and decision model
The Graph is load-bearing for discovery and live state, but the agent must independently verify the source 
transaction before authorising LP funds. This prevents a compromised indexer or stale query from being 
sufficient to drain the vault.
Mandatory source checks:
 Transaction succeeded and targeted the approved ArcaidiaIntentRouter.
 IntentCreated exists and fields match the candidate intent.
 CCTP transfer was initiated for the same amount/destination flow.
 Token is approved USDC and destination is Arc.
 Source transaction meets configured confirmation threshold.
 Intent ID / source transaction has not already been filled.
 Deadline is still valid.
Deterministic risk inputs:
Signal Example policy
Available destination-chain liquidity Must cover output while preserving reserve floor.
Single-intent cap Reject above configured maximum.
Outstanding unsettled exposure Reject if post-fill exposure exceeds cap.
Vault utilisation Higher utilisation increases fee or causes rejection.
CCTP backlog / oldest unsettled age Increase fee or pause new fills when settlement is delayed.
User maxFeeBps Quoted fee must never exceed it.
Confirmation policy May scale with intent size; hackathon demo may use a low 
testnet threshold.
The LLM, if used, may explain or recommend parameters. Capital-safety constraints and final ACCEPT/REJECT 
gates must remain deterministic and unit tested.

8. FillAuthorization and destination LiquidityVault
The agent should not have an unrestricted 'send vault money' method. It signs a narrow EIP-712 authorisation 
which the destination contract verifies.
Recommended signed payload:
Field Rule

ArcaidiaLiquidityVault checks the authorised solver signer, intentId unused, nonce unused, expiry, amount

Circle Agent Wallet policy should additionally restrict allowed contract(s), asset(s), per-transaction value and 
daily value. This creates two independent control layers: wallet policy plus smart-contract policy.

10. Liquidity provisioning and economics
For the one-way V1 demo, only Arc requires fast-fill LP inventory. Ethereum requires the source router/CCTP 
path, not a fast-liquidity vault. Add an Ethereum LP vault only when bidirectional fast fills are implemented.

The 1 USDC difference is gross execution revenue. It can be split between LP, solver and protocol. For the 
hackathon, keep accounting explicit but simple.

 Monitor fast-filled but not canonically settled intents.

 Submit any required destination transaction idempotently.

14. Business model and product position
Arcaidia monetises the time value and risk of destination liquidity, not the existence of canonical bridging. The 
user pays a fast-execution fee; LPs earn for advancing capital; the solver can receive a share for 
pricing/execution; the protocol can retain a share.
 Customer promise: express an outcome, receive destination USDC quickly, and let infrastructure settle 
underneath.
 LP value: fee income on short-duration inventory advances backed by already-initiated canonical 
settlement.
 Protocol moat: solver/risk data, liquidity network, execution policies and future multi-asset routing.
 V2 expands from 'USDC here  USDC there' to 'asset A here  desired asset B there' using Uniswap.→ →
 V3 makes solver/discovery services machine-payable through Hedera/x402.

16.3 Deterministic CREATE2 deployment
All symmetric Arcaidia protocol endpoints MUST be deployed through CREATE2 so corresponding contracts 
resolve to the same addresses on Ethereum and Arc wherever the underlying chains support the same CREATE2 
semantics. Claude Code must treat same-address deployment as a V1 acceptance criterion, not an optional 
optimization.
 Use identical creation bytecode and deterministic salts for corresponding deployments.
 Chain-specific USDC addresses, CCTP domains and Circle contract addresses MUST NOT alter the CREATE2 
init-code hash if identical endpoint addresses are required.
 Therefore use deterministic deployment followed by tightly controlled chain-specific 
initialization/configuration, or an equivalent pattern that preserves identical init code.
 Deployment tests must calculate expected CREATE2 addresses before broadcasting and assert the deployed 
address on both chains.
16.4 Asset configuration: MockUSDC and real USDC
Core protocol logic operates against one configured IERC20 settlement asset. MockUSDC and real USDC are not 
separate code paths. Development uses a mintable OpenZeppelin ERC20; production/qualifying configuration 
points the same protocol interfaces at real USDC.
local/dev config: settlementAsset = MockUSDC
production config: settlementAsset = USDC
Do not implement a runtime boolean such as useRealUSDC. Asset selection belongs to deployment/configuration 
so changing asset does not re-orchestrate the application or change agent logic. Both chain vaults are funded in

18. CCTP availability as an agentic risk signal
Canonical settlement is intentionally asynchronous. Circle attestations can remain pending while source 
confirmations are reached, and delayed/stuck settlement must be treated as an economic exposure condition 
rather than hidden as an infrastructure inconvenience. The user fast path does not wait for canonical 
completion, but LP inventory remains exposed until CCTP reimbursement completes.
The Liquidity Agent SHOULD continuously derive or observe at minimum:
 oldestUnsettledIntent - age of the oldest fast-filled but canonically unsettled intent.
 pendingCCTPValue - aggregate principal currently advanced by LPs and awaiting canonical reimbursement.
 averageSettlementLatency - recent observed canonical settlement time, preferably with a rolling window.
 vaultLiquidity - currently deployable destination liquidity after reserve requirements.
 CCTP/Iris health - whether required Circle message/attestation services are reachable and progressing.
The risk engine then responds deterministically:
Circle normal      -> ACCEPT normally
Circle slowing     -> increase required fee and/or reduce maximum fill size
Backlog too large  -> REJECT new fills that would breach exposure policy
Circle unavailable -> PAUSE new fast fills; Settlement Agent continues recovery/reconciliation

24. V2 and V3 extension contracts

25. Final V1 judge pitch
Arcaidia does not replace canonical settlement. The user's USDC is committed to Circle CCTP first. 
Autonomous liquidity agents observe that committed settlement, independently verify it, price the risk, and 
decide whether to advance destination liquidity from an destination LiquidityVault. The recipient receives 
USDC quickly; CCTP completes asynchronously and reimburses the LP. Onchain contracts hold truth and funds, 
The Graph supplies live observation, and Circle Agent Wallets provide bounded autonomous execution 
authority.
That is the V1 architecture. Do not broaden scope until this path is demonstrably reliable.
